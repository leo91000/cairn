# Owner package and instance read contracts

Measured locally on 2026-10-21 against synthetic packages and saved instances.
The reference is the complete `/api/plugins` response in the same binary,
retaining its data contract. The candidates are the **first** compact package
page, the **first** selected-package instance page, and one exact instance read.
These return different information and datasets; this is not an A/B benchmark
of releases or a comparison of equivalent complete results.

Reproduce alone from the repository root:

```sh
PATH="$PATH:/usr/sbin" CARGO_BUILD_JOBS=1 CARGO_INCREMENTAL=0 CARGO_PROFILE_DEV_DEBUG=0 CARGO_PROFILE_TEST_DEBUG=0 mise exec -- pnpm test:backend -p cairn-installation --test plugin_catalogue measure_catalogue -- --ignored --nocapture --test-threads=1
```

The [raw observation](plugin-catalogue-reads.json) includes all samples, source
hashes and host conditions. The fixture copies 40 packages containing 79 valid
versions, each with six 10,000-character TOML defaults. Each input manifest stays
below 65,536 bytes; escaping its literal quotes roughly doubles its JSON size.
Source consists of two tiny Luau files per version. Forty paused instances of
one package store matching six-field settings and no credentials or grants.
Fixtures are created before timing. The instance page contains 32 of these
instances; the exact read contains one. UUIDs are generated by the fixture, so
first-page membership and its byte count can vary slightly between repetitions.

| Local measurement | Complete response | First package page | First instance page | Exact instance |
| --- | ---: | ---: | ---: | ---: |
| Encoded response bytes | 19,226,147 | 20,599 | 3,857,676 | 120,548 |
| First API read wall time, ms | 4413.769 | 1917.239 | 1966.978 | 948.919 |
| First API read process CPU, ms | 4417.707 | 1919.692 | 1966.753 | 948.915 |
| Five warm reads, median wall time, ms | 4299.026 | 2017.838 | 1949.752 | 1079.248 |
| Five warm reads, median process CPU, ms | 4302.023 | 2020.359 | 1949.730 | 1079.334 |

Six observations of the existing registry approval write path have median wall
time **52.841 ms** and process CPU **53.517 ms**. All reads use that unchanged
approval write and stored record format. No summary, index, token or manifest is
newly persisted by the read APIs.

The [earlier observation without configured instances](https://github.com/leo91000/cairn/blob/6d73793899bd0592937ae0db39f2720031174e68/docs/performance/plugin-catalogue-reads.json)
is preserved in Git. Its workload differs from this one; the two observations
are not used to claim a performance regression or improvement between revisions.

The first request is cold only with respect to its API; OS page caches remain
warm from fixture creation. The complete response is measured first, followed by
cards, the instance page and the exact instance. Warm rounds reverse that order
on alternate rounds. Reads include routing, file validation/hashing, database
actor work, JSON serialization and collecting the response body. They exclude
client parsing and network/Beacon latency. Process CPU includes all threads of
the test process. Approval timings include existing validation and its database
transaction, rather than only an isolated SQL upsert.

Conditions: Linux 6.12.109 x86_64/glibc 2.36, seven virtual CPUs, about 18.6 GiB RAM;
load average at launch 1.23/3.05/3.35. All test suites, compilers, Node builds,
PostgreSQL and the managed AOSP emulator had stopped before this isolated
measurement. The coding agent and shared VM scheduler remained active. These
timings establish no production latency guarantee.

The compact and instance pages stay within half the 8,000,000-byte relay limit;
the complete reference exceeds that limit. Functional cases separately follow
**all** package, version and instance cursors, enforcing count and byte bounds.
A distinct valid eight-field instance fixture forces a byte-limited page before
the 32-item limit. Exact reads preserve complete grant IDs, and changed module
bytes still reject stale approval digests.

These results expose remaining CPU work. Cards validate every installed version
of each selected package to derive approval state. Instance reads also inspect
the package to match its worker/readiness semantics; the dense package here has
40 versions. Work is therefore not bounded solely by the response size or item
count. Web/Android cards and version review now use these separate contracts;
instance/detail screens and grant selectors still require their own migration.
