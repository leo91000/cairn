# Generated Rust contracts

Issue #401 qualifies the toolchain selected by #396/#397 for the first converted
capability. The Rust DTOs in `crates/contracts` own the wire fields. The installation's
`capabilities` module owns its verified context, policy and handler. It appends one
operation to the existing shared MCP catalogue; the other operations stay unchanged.
There is no generic dispatcher or persistent-format change.

`resume_run` uses the existing worker's `resume_authorized` path. It requeues the
same run with its workspace/session/checkpoint, resets the existing manual recovery
budget and preserves fencing. `run_task` and retry still create a new run. Cancellation
while recovery is pending records the cancellation request; the worker settles it
once fencing completes. The capability never bypasses that process.

The HTTP route returns `{ "runId": "…" }`. The generated error DTO describes the
existing HTTP `{ "error": "…" }` body; status remains an HTTP status. MCP retains
its existing protocol error envelope. The UI reloads run state through its existing
live feed rather than interpreting a duplicate run snapshot in the command response.

## Reproduce generation and qualification

Use the repository's pinned Rust, Node/pnpm, JDK 21 and Android Gradle wrapper:

```sh
pnpm generate:contracts
pnpm check:contracts
pnpm test:backend -p cairn-contracts
pnpm exec vitest run apps/web/tests/resume-contracts.test.ts
apps/android/gradlew -p scripts/contracts-kotlin test --no-daemon
```

`check:contracts` regenerates all owned outputs, then rejects changed or untracked
outputs. CI runs it, compiles the generated Kotlin models and decodes the shared
corpus. The web build and Android builds compile their generated calls/models too.
No generated model is patched; the generation command applies the same pinned
ESLint/ktfmt formatters as the rest of the repository.

| Tool | Exact version | Responsibility |
| --- | --- | --- |
| schemars | 1.2.3 | serde DTOs to JSON Schema draft 7 |
| ts-rs | 12.0.1 | Rust DTOs to TypeScript |
| json-kotlin-schema-codegen | 0.123 | the same schemars export to Kotlin |
| Kotlin serialization plugin | 2.3.10 | generated serializers |
| kotlinx-serialization-json | 1.10.0 | Kotlin encoding/decoding |
| ktfmt | 0.64 | deterministic Kotlin formatting |

The bounded Mustache templates cover objects, string UUIDs, nullable/omitted fields,
boolean defaults, lists, homogeneous string-keyed maps, bounded integers and tagged
object unions (`kind`). They use the generator's own type analysis, composite-target
API and reference resolution. They neither parse JSON Schema themselves nor map
business unions to `JsonElement`/`Any`. Unsupported untyped values emit
`UNSUPPORTED_TYPE`, which fails compilation. Extend only for a demonstrated next
command, and rerun qualification before doing so.

Input schemas describe deserialization; output schemas and the Kotlin composite
model use schemars' serialization contract. This preserves required explicit-null
fields separately from optional fields omitted by Rust. `qualification-wire.json`
is generated by serializing the corpus in Rust, and TS/Kotlin tests compare their
wire objects against it, including key presence, rather than only round-tripping
within one decoder.

The composite-target API matters: separate schemars documents with embedded
union definitions can produce an `Any` reference and optionalized required fields
with upstream defaults. Registering all `definitions` through `generateAll` resolves
the reference to its generated sealed interface. Maps use serializable inline wrappers.
The custom templates provide kotlinx annotations and discriminator serial names.

`tests/fixtures/resume-contracts.json` is shared by Rust, TS/Ajv and Kotlin. It tests
defaults, absent and explicit-null fields, both tagged variants, UUIDs, lists/maps,
integers at ±(2^53−1), and the HTTP error body. Rust and Kotlin round-trip the decoded
values. Overflow, unknown variants and invalid UUIDs are rejected. Kotlin's standard
numeric decoder also accepts a numeric string; `serverInvalid` records that known
client-decoder permissiveness, while Rust and JSON Schema reject it. The server
remains authoritative. TS types alone do not validate JSON or install defaults;
the corpus checks the generated schema with Ajv, including its default application.

## Authorization and remaining conversion

The adapter supplies a verified human account, public grant scopes, or installation
execution bearer. The capability never reads identity from command JSON. It rechecks
installation grants and native provenance in the worker's resume transaction, after
asynchronous preparation and the worker lock. Public `run` scope does not supply a
human native-execution proof. Existing native caller/delegation ceilings stay intact.
No Beacon account operations or new rights are introduced.

Generated clients replace the raw resume routes in the web and Android run screens
and chat recovery controls. The remaining catalogue, persistence and other client
models are outside this pilot. Their existing writers and schemas stay in place
until their own conversion tickets; no new compatibility layer or SQL adapter was added.

## Beacon account app contracts

Both apps use generated account method models and calls from
`crates/contracts/src/beacon.rs`. The read executes at Beacon with its existing
account-session policy. These app contracts are outside the agent catalogue per
[the owner arbitration and action inventory](BEACON-CAPABILITIES.md). B6 (#421)
removes the tool descriptor, empty input and agent-only refusal introduced by #436.
The shared account corpus qualifies the remaining app response in Rust, TS and Kotlin.

## Projects: first SQL domain (#402)

The project lifecycle extends the B1 registry and generation command. `save_project`
creates from `{creationId?, settings}`; `replace_project` replaces all settings from
`{projectId, revision, settings}`; `get_project`, `list_projects` and `delete_project`
complete the shared HTTP/public MCP/installation operations. HTTP uses `/projects`
and `/projects/{projectId}`; listing returns `{projects: [...]}`. Creation replays
return the current project without overwriting later edits. Every replacement
requires the current revision, generates a fresh revision and retains `createdAt`.
Web and Android keep their existing editors and retry identities, using generated
models and calls. Plugin import keeps its existing API for B3 and registers through
the same typed writer. No new authorization scope is introduced: public reads use
`read`, writes use `manage`, HTTP writes require the owner, and installation reads
and writes recheck their execution grant in the database transaction.

`projects` has explicit columns for id, name, canonical path, source mode, base
branch, description, origin, the four nullable plugin-source fields, revision,
creation time and update time. The source columns are all null or all present.
SQL checks source mode, required/bounded text and the wire timestamp range; indexes
cover update ordering and plugin/item lookup. Paths retain their existing behavior:
registration canonicalizes and confines them to configured workspace roots; several
registrations may name the same path. There is no new uniqueness rule or historical
migration. References from agents, missions and active work retain their existing
transactional validators until those domains gain tables. Completed run snapshots
remain intact on deletion. There are no cascading deletes into other domains.

The generic records writer rejects projects; all current reads use `Db::project`
and `Db::projects` (or their async Store methods). JSON serialization remains only
at the boundaries of run snapshots, archive/credential preparation and other
unconverted domains. A2–A18 replace those owning domains; A18 removes the remaining
adapters. SQL mapping is local to `projects.rs`, without a generic repository or ORM.

The new shared corpus `tests/fixtures/project-contracts.json` qualifies defaults,
creation omission, required settings, source metadata and project wire output in
Rust, TS and Kotlin. UUID version 4 for creation identities is a server rule beyond
JSON Schema's UUID format; clients never grant authority through validation.

### Development reset

The fresh installation schema is now version 4. Earlier development databases
are rejected, without being rewritten. Stop the development processes, remove the
**disposable development data directory** (SQLite, vault and related local state)
and start with a newly empty data directory. Recreate projects/agents and rerun
fixtures. Do not point a development reset at an existing installation. No migration
or legacy-data reader is shipped, and this change does not reset or deploy anything.

### Local storage qualification

```sh
pnpm test:backend -p cairn-installation --test project_measurement -- \
  --ignored --nocapture --test-threads=1
```

The opt-in harness compares the records SQL mapping at `40349271` against the
current typed SQL methods in one build, using identical complete project values.
It runs five alternating-order repetitions of 1,000 inserts/replacements/deletes,
1,000 point reads, 50 lists of 1,000 rows and 100 connection-cold reads. Two complete
point-read warmups precede measurements. It reports p50/p95, process CPU, wire bytes,
DB bytes, live WAL bytes and pages by table/index. Cold means a fresh connection and
statement cache; the OS page cache remains warm. Connection opening is excluded from
read latency and included in its separate CPU total. Deletion measures the database
write, with audit, without reference-checking scans in either variant. This is a
local SQLite layout comparison, not an HTTP/actor/clone benchmark or production
network latency. Store pool initialization and corpus construction are untimed.
Raw results belong outside Git; PR descriptions record the command, SHAs, host
conditions, result summaries and limitations.

## Agent profiles, preview and avatars (#403)

`crates/contracts/src/agents.rs` owns `AgentSettings`, the public profile and the
complete creation/replacement, preview, merge and avatar commands. The same ten
operations extend the existing registry for HTTP, public MCP and
`cairn_installation`. Listings return `{agents: [...]}`. Replacements and previews
require `{agentId, revision, settings, review}`; there is no partial update route.
Creation retries return the current profile without overwriting later changes.
`review` holds explicit owner confirmations, separately from settings. Public and
installation agents cannot add plugins, exclusivity, native execution or broaden
rights; this slice does not construct an owner-confirmation workflow for agents.
Preview reads a consistent transaction without writing or notifying subscribers.

The `agents` table stores identity, provider, text, timeout, revision, timestamps
and avatar metadata in named columns with SQL checks and an ordering index.
Permissions are relational since A3 (below). Only unconverted run/plugin/node
consumers serialize typed profiles at their snapshot boundaries. Avatar image bytes keep their existing private key/value storage. Merge
preserves its existing run/task/chat effects and permission rules. No historical
reader or migration is shipped. Generic records cannot store profiles.

Both apps use generated profile, permission, preview and avatar models and clients.
Manual Zod schemas and Kotlin data classes for this domain are removed. Defaults
come from Rust; scalar/list defaults and string-pattern checks extend the pinned
Kotlin templates. Commands use the generated canonical JSON encoder with defaults
and explicit nulls, preserving null (all resources) versus an empty selection.
The permission object, tool map, plugin/exclusivity lists and review object are
required so omitted settings cannot silently clear grants on replacement.
Unknown providers are rejected, including in saved snapshots. Schemars metadata
also carries resource/review UUID formats and selection counts, skill lengths,
and MCP map-key, tool-count and tool-name bounds. The shared malformed selection
corpus and schema boundary cases check these against Rust validation and both MCP
capabilities.

`tests/fixtures/agent-contracts.json` qualifies the same values in Rust, JSON
Schema/TypeScript and Kotlin. Agent editor journeys exercise both apps; the two
MCP interfaces exercise the same profile, preview and avatar commands. Uploads
use the generated JSON/base64 command and retain the existing 5 MiB image limit;
private authenticated image delivery is unchanged.

The A1 storage harness above also measures profiles (`agent_storage_layouts`),
against the records mapping on the A2 base. It reuses the same repetitions and
read/write phases with 1,000 complete mixed-provider profiles, long instructions,
nullable permissions and avatar metadata on half the rows. Pixels and transport
are outside the measured layout. Reference and candidate serialize identical wire
values. The candidate replacement includes the expected-revision read. PR reports
record results and host conditions; raw measurements are never committed.

## Agent permissions: one relational authority (#404)

The existing generated `AccessPolicy`, `AgentSettings`, replacement and preview
commands remain the wire contract on web, Android, HTTP, public MCP and
`cairn_installation`. A3 removes the three JSON permission columns from `agents`.
`agent_permissions` stores backend, sandbox, installation/delegation powers and
four explicit wildcard flags. Ordered `agent_projects`, `agent_skills`,
`agent_nodes`, `agent_mcps`, `agent_plugins` and `agent_exclusive_nodes` store the
selections. `agent_mcp_selections` represents an explicit tool selection even when
empty; `agent_mcp_tools` stores its ordered tool names. Null, an empty selection,
and an omitted MCP tool selection keep their distinct meanings. Duplicate input
selections normalize to their first occurrence.

Agent FKs cascade on deletion; project FKs restrict deletion. CHECKs bound boolean
flags, supported backend/sandbox values, text and list positions; unique keys
prevent duplicate grants. Permission tables use WITHOUT ROWID so composite keys
do not duplicate a separate rowid/primary-key index. Listing loads each relation
once for the whole catalogue. Reads hydrate one SQLite snapshot, and profile/permission
writes publish atomically. Revisions change on owner saves and resource revocation.
There is no historical reader or migration: the initial schema is version 4.

The A2 mirror, resource reconciliation, Value permission writer and node
configuration's `exclusiveAgents` input are removed. Resource wire lists are
read-only projections from the relations, attached only at the unconverted
node/plugin boundary. The records writer drops those fields before storage.
Enforcement and resource views therefore share one authority. Plugin setup's
existing initial grant command and node enrollment's additive grant command write
typed profiles in the same transaction; they do not write resource copies.

Existing capabilities advertise the owner-only permission ceiling. Installation
and public MCP agents cannot broaden permissions, add plugin/exclusive grants,
review native admission or reapprove delegations. No boolean confirmation in an
agent command confers owner authority; A3 adds no agent confirmation workflow.
Live plugin/exclusive revocation and saved run/delegation policy rules stay intact.

Deferred foreign keys, tracked in contraction ticket #433: node/exclusive node
IDs (A9/A10, #410/#411), MCP server and tool selection IDs (A14, #415), plugin instance IDs (A12, #413),
and file-backed skill keys (A16, #428). These use the existing business validators;
node and MCP targets are checked again in the publication transaction, and only
active agent-capable packages can receive new plugin grants. Already held grants
remain editable while their package awaits review. Skill selections retain their
existing named-filter semantics, including absent skills; they confer no access
to an unselected project. No cross-database FK to Beacon is introduced.

The opt-in `agent_storage_layouts` case of the shared `project_measurement` harness
now compares the frozen A2 SQL/JSON mapping at `ff1f95ef` with A3 relations. It
uses the same alternating repetitions, warmups, read/write/list phases and CPU,
DB/WAL/page reporting as A1/A2, with mixed wildcard/empty/selected grants and MCP
tool selections. The reference mapping is test-only. Raw measurements stay out
of Git and local SQLite timings do not include production network latency.

## Missions and scheduled commitments (#405)

`crates/contracts/src/missions.rs` owns mission settings, their public view, creation,
complete replacement, state, deletion and cron preview commands. `list_tasks`,
`get_task`, `create_task`, `replace_task`, `set_task_state`, `delete_task`,
`preview_schedule` and `list_task_activity` extend the existing capability registry.
HTTP lists return `{tasks: [...]}`. Replacements and state changes require `taskId`
and the current `revision`; creation retries retain their identity and return the
current mission without recomputing the schedule. The installation adapter retains
the calling agent as the creation default; the public contract requires an explicit
agent. Scope checks remain `read`/`manage`; deletion remains owner-only in the apps.
Members can edit their own commitments and pause/archive another author's mission,
but cannot resume or restore it, change its content, or recover its creation identity.

The initial SQLite schema v4 adds `missions` with named scalar columns, agent/project
foreign keys, update/reference indexes and a partial due-time index. Ordered
`mission_tags` and `mission_skills` preserve selections, duplicates and their order;
`skills_inherited` distinguishes all allowed skills (`null`) from an empty selection.
An SQL trigger forbids changing the author or membership identity and undoing an
observed removal. Wire timestamps, booleans, lengths and schedule/failure consistency
have SQL checks. Relations cascade only when the mission is deleted; retained runs
and their snapshots never cascade. `records` cannot store missions.

`missions::Missions` owns the private author mutex: Beacon observations, saves,
deletions, schedule admission and agent transfer share its ordering. Beacon has no
comparable policy generation, so the mutex remains rather than weakening this
ordering. No caller acquires it and no `_locked` API is exposed. Membership is
captured at creation and never backfilled; removal/reinvitation cannot revive an
old commitment. A partition defers admission with its due time intact. Preparation
still freezes mission settings, profile/projects and skill bundles; author eligibility
is checked again after that preparation. Already admitted runs, durable waits,
fencing and `resume_run` retain their existing behavior.

Both apps use generated mission models and commands, without manual Zod or Kotlin
mission data classes. Android also shows the same author restrictions and scheduling
wait/removal reasons as the web, in French/native controls. Run task presentation
uses generated `RunTaskSnapshot`: chat runs synthesize typed settings without creating
a mission. JSON remains only at the unconverted run/native-node boundaries (A5/A10),
including typed native provenance lists and nullable plugin grant lists in named SQL
columns. Connection/revision/external-author lineage from ADR-0068 survives mission
replacement, restrictive state changes, restart and launch; revocation still uses
the live native policy. `list_task_activity`
returns the existing run-summary shape until the run conversion; its input and policy
are registered here. It uses the authenticated account's read state in the apps and
the owner's current read state in agent tools, without initializing that state on
an agent read. No historical format, fallback reader or migration is included.

`tests/fixtures/mission-contracts.json` qualifies defaults, null/empty skill selections,
creation identities, command bounds and wire output in Rust, TypeScript and Kotlin.
The existing author, worker, retry, read and mission-chat suites exercise the same
commands against fresh fixtures. The A1/A2 `project_measurement` harness adds
`mission_storage_layouts`, retaining the alternating five repetitions, warmups,
1,000 writes and point reads, 100 fresh-connection reads and 50 lists, plus 50 due
queries selecting 500 of 1,000 missions. It compares the records mapping on the A4
base with typed SQL in the same build and corpus; preparation of the referenced
profile is untimed. Measurements and line accounting belong in the PR, outside Git.
