# Audit des conversations et de l'environnement des agents

Observation du 13 septembre 2026, jusqu'à 18:54 UTC. Application déployée :
`207ca4f95dc72f30972a187afec84381555cd628` (`v0.19.0`).

Audit en lecture seule : 26 runs, 6 conversations, 13 565 événements au dernier
relevé. 23 runs réussis, 2 échoués, 1 actif. Le run Android reste actif ; ses
résultats de compilation et de tests ne constituent pas encore un bilan final.
Les événements de commande ont été rapprochés des résumés, du code actuel et de
la configuration du VPS. Les occurrences dans du code affiché, les commandes de
recherche sans résultat et les tests de refus d'accès attendus ont été écartés.
Aucun agent interrompu, aucune permission ni image modifiée.

## Priorités

### 1. Vérifier les permissions GitHub avant les travaux de CI

**Confirmé et toujours actuel.** L'en-tête `X-OAuth-Scopes` du compte utilisé par
le manager contient `admin:public_key, gist, read:org, repo`, sans `workflow`.
Les pushes Eliah ont effectivement été refusés pour modification de
`.github/workflows/ci.yml` (événements 829 et 5925).

Le run `f7fbe85e-9102-4978-8ff4-9cae95556d1e` a terminé en `succeeded`, mais son
résumé indique que le commit `4f07b442` n'a pas pu être poussé pour cette raison.
Le chat Android prépare également un workflow ; il peut rencontrer le même refus.

Le login GitHub de `crates/installation/src/connections.rs` ne demande pas de scope
supplémentaire. Prévoir une connexion capable de demander `workflow`, vérifier les
capacités après connexion et afficher une action de reconnexion si nécessaire.
Ajouter le scope nécessite une autorisation GitHub ; il ne s'agit pas d'un droit
Linux à ajouter à l'image. Ne pas modifier les identifiants du run actif pendant
cet audit. La CLI propose l'extension des droits via
[gh auth refresh](https://cli.github.com/manual/gh_auth_refresh).

### 2. Éviter les nouvelles conversations basées sur un checkout périmé

**Confirmé et toujours actuel dans la préparation.** Le checkout source
`/workspaces/cairn-installation` est à `1e0d71b` du 9 septembre ; celui d'Eliah est à
`c173f6d8` du 8 septembre. `prepare_project` dans `crates/installation/src/execution.rs` clone
la branche locale du projet puis remplace l'URL du remote, sans actualisation.

Le run Android `adc8734d-34be-4223-9295-0602f8c5754f` a commencé sur cette ancienne
version. Son premier `git fetch origin` observé (10864, 16:39 UTC) a récupéré
`1e0d71b..207ca4f`, environ 48 minutes après le début du run. L'agent a explicitement
signalé devoir refaire le thème et adapter les contrats API (10860 et 10963).
À l'événement 13101, il travaille bien sur `207ca4f` : ce chat s'est corrigé, mais
la source des prochains chats reste ancienne.

Préparer les nouveaux travaux GitHub depuis un SHA récent et enregistré de la
branche distante. Conserver un mode explicite « snapshot local » pour les travaux
qui le demandent. Ne pas écraser le checkout source, les modifications locales ou
les disques de conversations reprises. Tester également la préparation depuis
un clone partiel et les échecs réseau.

### 3. Donner un environnement Android persistant et prévisible

**Friction observée, déjà contournée par le chat actif.** Au démarrage, `java`,
`gradle` et `sdkmanager` n'étaient pas disponibles (9422). L'agent a installé les
JDK Temurin 17 puis 21 via mise (9563 et 10223), ainsi que le SDK Android.

Le premier SDK était dans `/tmp/cairn-android-sdk` (9661). Or `/tmp` est un tmpfs
recréé par `deploy/microvm/init` : ces fichiers occupent de la RAM et ne survivent
pas au redémarrage. À 18:13 UTC, le SDK a été réinstallé dans
`/data/runs/<run-id>/output/android-sdk` (12589), qui est persistant. Ne pas annoncer
ce problème comme encore bloquant pour ce chat : son contournement est établi.

Prévoir un JDK LTS géré par mise et un bootstrap Android à la demande, avec
`ANDROID_HOME` dans le home persistant, les outils CLI Android, et les versions
SDK/build-tools choisies par le projet. Utiliser le Gradle Wrapper du projet.
Un répertoire de cache dédié convient mieux que le répertoire des livrables.
Ne pas ajouter tous les SDK et images système à la base commune.
La [documentation des variables Android](https://developer.android.com/tools/variables)
décrit les emplacements configurables.

### 4. Distinguer tests Android JVM et véritable test sur appareil

**Limite de capacité.** Les vérifications observées utilisent Robolectric et des
captures de composants. `/dev/kvm` n'est pas exposé dans les invités actuels ; le
run l'a sondé sans trouver le périphérique (9855). Le noyau et le lancement de VM
ne provisionnent pas un service d'émulateur Android accéléré.

Ajouter des droits `chmod` ou `sudo` ne crée pas cette capacité. Pour une vraie
validation sur appareil, prévoir un émulateur ou appareil Android dédié, avec un
accès ADB contrôlé par run, puis tester connexion, notifications, caméra/fichiers
et reprise de l'application. La possibilité d'une virtualisation imbriquée dans
notre configuration Firecracker n'a pas été établie pendant cet audit.
Voir les [prérequis d'accélération Android](https://developer.android.com/studio/run/emulator-acceleration).

### 5. Faire apparaître les objectifs bloqués malgré une exécution réussie

Le statut actuel peut signifier que Codex s'est terminé correctement alors que le
résumé explique que le résultat demandé n'a pas pu être livré. Le blocage GitHub
du run `f7fbe85e-9102-4978-8ff4-9cae95556d1e` en est un exemple concret.

Séparer le statut technique de l'exécution d'un résultat structuré de la tâche
(terminée, bloquée, action utilisateur requise), accompagné de preuves de livraison.
Éviter de déduire ce résultat par recherche de mots dans les logs : un test qui
échoue pendant le développement peut ensuite être réparé.

## Erreurs historiques et limites du diagnostic

- Les deux runs réellement `failed`, `fa43789b…` et `fd3f6ad8…`, ont échoué le
  10 septembre en clonant Eliah : objets manquants du remote promisor, puis EOF.
  Le checkout source reste configuré `promisor=true`, `partialclonefilter=blob:none`.
  Le mécanisme de clonage local est encore présent. Le défaut historique est
  prouvé ; un nouvel échec avec les objets actuellement disponibles n'a pas été
  provoqué sur le VPS. Ajouter un test de régression avec clone partiel avant de
  changer cette préparation.
- Les anciens manques Python, bibliothèques Playwright et Docker datent d'avant
  la boîte à outils actuelle ou Firecracker. Les tests de l'image actuelle
  couvrent ces capacités ; ces anciens logs ne justifient pas de nouveaux droits.
- Les refus d'écriture des agents explicitement configurés en lecture seule sont
  attendus. Le mode YOLO dispose déjà de `sudo` sans mot de passe dans sa VM ;
  le mode restreint retire cette possibilité.
- Les 404 de téléchargement ktfmt (10310, 12661) portent sur une URL/version
  recherchée par l'agent, pas sur un manque de permission réseau.
- Les échecs Kotlin/Compose, recherches de fichiers absents et tests applicatifs
  en cours ne démontrent pas une panne de l'image. Le run Android travaille encore
  dessus : ne pas présenter ses tests intermédiaires comme le résultat livré.
- Aucun OOM, disque plein ou nouveau refus Linux bloquant n'a été identifié dans
  les sorties analysées. Cela ne remplace pas une surveillance continue du noyau.

## Ressources observées

Le VPS dispose d'environ 691 Gio libres et 33 Gio de RAM disponible au relevé.
Les disques privés occupent environ 16 Gio, dont 9,2 Gio pour le chat Android.
Chaque VM reçoit actuellement 2 vCPU et 4 Gio de RAM. Une configuration de
ressources par agent/projet peut être utile pour Gradle et les émulateurs ; aucune
augmentation globale n'est justifiée par un OOM observé ici.
