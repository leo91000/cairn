# Android 0.6.0 / web parity

Performance diagnostics: web now matches Android's default-on, account-bound,
foreground-only upload, opt-out, local refresh/reset/copy and native sharing where
available, including without a selected installation. Personal account diagnostics
are UI-only, outside installation MCP/agent grants. Both retain the same Beacon
account authorization, 64 KiB request cap, six uploads/minute/account, 256 windows
and 14-day retention. Android retains schema 1, device/heap metadata and native
frame metrics; web uses closed schema 2, frontend source-build identity, browser
family, API outcome/pending counts, JSON/Markdown timings and event-loop/Long Task
observations where supported. These browser measurements do not represent GPU
frames. Web opt-out is shared across Beacon subdomains; Android remains a phone
preference. See ADR-0043. Coverage: model/monitor/uploader/build identity unit tests,
Beacon telemetry integration tests, browser account/settings diagnostics journeys;
existing Android diagnostics tests cover its unchanged native implementation.

## Mermaid diagrams in Markdown (2026-10-29)

Both layouts reserve the asymmetric flag notch when sizing multiline node labels.
Group borders share separation constraints across ranks, keeping sibling groups and unrelated nodes outside each other's frames.
Group titles use the reserved space at the physical top in every direction.
Sequence parent frames include the complete drawn bounds of nested frames, including short labels and empty children spanning unused participants.
Nested sequence backgrounds paint parent before child, behind lifelines. The web viewer refreshes its layout when app fonts finish loading; Android measures its bundled typefaces synchronously. Automatic Fit follows that refresh, while manual zoom and pan stay in place.

Both apps draw closed ```` ```mermaid ```` (or `mmd`) fences in chat Markdown as native
diagrams: flowcharts (directions, node shapes, subgraphs, link styles, heads and labels,
`classDef`/`class`/`style`/`linkStyle`, http(s) `click` links, front-matter titles), state
diagrams (start/end, composite states, choice, fork/join, notes), sequence diagrams
(actors, every arrow kind, activations, notes, `loop`/`alt`/`opt`/`par`/`critical`/`break`/`rect`,
`autonumber`, including start/increment values to hundredths, and semicolon-separated steps
including after the header) and pie charts. Encoded semicolons stay in sequence labels. Large pie totals
move to a full-value legend row, with a sum symbol in the center so digits do not cross the ring. Zero-value categories stay in the legend without an arc. Neither app loads Mermaid or a WebView: `diagram.ts` /
`Diagram.kt` parse the same model and `diagram-layout.ts` / `DiagramLayout.kt` compute the
same scene, drawn as SVG on web and on a Compose canvas on Android with one light/dark
palette. A fence stays code until its closing fence arrives, so streaming never flickers;
unsupported types (gantt, class…) keep the code block, and invalid sources show their code
with a short note. State notes stay physically left/right of their target in every direction;
multiple notes stack with reserved space. Notes on composite states or self-transition states
keep readable source. Links between a group and its own descendants, self-transitions on composite states or subgraphs, and concurrent state
regions (`--`), and sequence participant creation/destruction or `box` groups also keep source with an explanation. Subgraphs with a differing local direction keep source unless
an external member link invokes Mermaid's documented parent-direction inheritance
([syntax](https://mermaid.js.org/syntax/flowchart.html#direction-in-subgraphs)). Each drawing has a source toggle, copy and a full-screen viewer with
zoom and pan, including two-finger translation while pinching. Node links remain usable in the card and the full-screen viewer; Cairn file links use the same installation routing and in-app file viewer in both presentations; dragging a
linked node pans without opening it. This is presentation of existing message text, so public MCP and
`cairn_installation` are unchanged: agents already read and write the Mermaid source.

Platform differences: Android shrinks oversized card previews further when their physical dimensions cannot fit Compose constraints; the full scene stays available in the viewer. Web labels in English, Android in French (« Logigramme »,
« Diagramme d’états »…). The web viewer downloads SVG with embedded app fonts and measured line advances, or PNG drawn with the loaded app fonts; Android shares a PNG with a unique URI per export, so an earlier recipient cannot read a later export through its existing grant. inside a list item or quote at full width, and also draws a fence implicitly closed by the
end of its list item or quote, which the web keeps as code.

## Project and skill lifecycle through the capability registry (B3, #418)

Both apps use generated Rust contracts and HTTP clients for project source
listing/import, the skill library, bundle/file reads and edits, archive import/export,
deleting skills and source status/update/forget. Their existing screens and native
pickers are unchanged. Web uploads raw blobs; Android uploads bytes selected with
the system document picker. These are the bounded raw transport of
`stage_skill_upload`; both agent tools can stage the same bytes as base64.
Archive exports use revision-pinned 512 KiB chunks on all surfaces, below the tool
result limit. HTTP, public MCP and `cairn_installation` invoke the same registry.
An execution must already hold the source instance grant; installation management
never supplies it and importing never changes project, skill or plugin grants.
Owner-only UI writes and source access remain owner-only. No visual or feature
difference between web and Android is introduced.

## Direct storage and overdue synchronization (2026-10-28)

Web and Android expose overdue synchronization while the agent continues on its
durable local journal. Both keep upload failures, unsaved bytes/age and the existing
integrity and disk-space warnings visible. The node storage setting now describes
a warning threshold rather than a deadline that suspends execution. REST, public
MCP and `cairn_installation` retain the same run storage payload, including
`backupDegraded`; provider capabilities and transfer keys remain internal.

## Skill suggestion frequency (2026-10-27)

Web and Android prefer frequently invoked skill names in `$` suggestions, within
the existing text relevance groups. Both use server `usageCount` from delivered
messages in the last 1,000 submitted messages and refresh it when opening the menu.
Counts are shared across devices and installation members; no local usage store
or platform difference. Access filtering, project shadowing and unused-skill
tie-breaks remain. Public MCP and `cairn_installation` expose the same counts through
`list_skills`, with their existing authorization checks.

## Node health and fleet summary (2026-10-28)

Both apps summarize the fleet (connected machines, slots in use, machines needing
attention) and give each node one health state with a short reason: ready, full,
busy, reserved, paused, updating, setup needed, needs attention, offline or
revoked. Failed updates or privilege changes and an agent's pending privilege
request count as needing attention; a runtime not yet ready without a reported
error, as after a budget change, is getting ready. The built-in runner needs
attention, and leaves the connected count, when its last usable report lags
machines the server reports online by the heartbeat timeout, or stays unchanged
for a minute of device time (it is refreshed on every listing when healthy); a
runner already stale when the page opens is found within a minute, and device
clock offset never matters. A runtime unready without a reported error reads not
ready, then needs attention once successful listings have seen it so for five
minutes. The fleet summary is computed by the shared `fleetSummary` on both
platforms. Native execution switched off with trusted people chosen reads paused;
a built-in runner no agent may use reads setup needed but is not counted as
needing attention. The first blocker wins, in the same order on both platforms
(`nodeHealth` in `packages/contracts/nodes.ts` and `data/Nodes.kt`); the
diagnostics list keeps its reasons, gains the stale-runner one and dates offline
machines with the same server-time reference when one exists (an online machine,
or a runner contact that changed while watched), and with the device clock
otherwise. Free slots and slot totals follow the runtime pool, as placement does.
Platform difference: web lists machines as compact rows and opens a side panel
(Overview, Access, Storage, Settings) whose existing editors and confirmations are
unchanged; Android keeps its Material cards and adds the health pill and reason
under each name. Health is derived from the existing `list_nodes` inventory,
already returned by public MCP and `cairn_installation`; no capability, grant or
command changes.

## Node priority drag and drop

Both apps let owners drag a node priority handle onto another row, then save the
agent's draft as before. Up/down buttons remain available for keyboard and
accessibility use; cancelling a drag leaves the draft unchanged. Web handles use
pointer capture for mouse, pen and touch; Android handles use native drag gestures.
This changes the presentation of existing ordered `nodePriorities`, already
editable through public MCP and `cairn_installation`; grants and placement rules
are unchanged.

## Quota waits in the Fil

Automatic quota waits, including admission waits and exhausted accounts, appear
with scheduled resumptions for conversations and missions on both clients. Web
shows “Waiting for quota”; Android shows « En attente de quota ». No reset date is
promised: undated waits follow dated resumptions and display availability rather
than a countdown. Questions, failures, pauses and exclusive suspensions retain
their existing priority. The conversation list now includes `accountWaitReason`
and `accountRequired` in HTTP, public MCP and `cairn_installation`; existing grants
are unchanged. Validation: Signal presentation tests, browser Fil quota journey,
and Android Signal journey.

## Feature map

Automatic agent placement: both apps offer VM only, native only and automatic
placement, with an ordered node preference list per agent (move up/down, remove,
add an authorized node). Preferences do not grant access; unavailable preferred
nodes fall back to other authorized capacity. Existing conversations retain their
environment until explicit migration. Web uses English buttons; Android uses
French Material controls. Public MCP and `cairn_installation` expose the same
generated `access.backend` and `nodePriorities` through agent create/replace.

Native disk capacity: web and Android show the same `list_nodes` disk-accounting
breakdown (local usage, unused grants, host free space and reserves, reclaimable
acknowledged backing, and last-reported unpublished journal bytes). Android uses
French Material text; web uses an English capacity section. Both explain overlapping
figures and immediate safe reclamation under pressure. Older runtimes may omit it.
The public MCP and built-in installation tool return the same inventory fields.

### Older history pages (#263)

Both clients reject pages from a replaced history or stream epoch, keep accepted
pages through subsequent emissions/reconnects, and persist the combined displayed
snapshot. Android extracts these rules into the pure `OlderPages` class while the
web keeps them in `useLiveRun`.
Android also cancels a page request when its path/API Compose scope is disposed;
the web guards application with its connection generation. The lifecycle stream
resume adapters remain in place. `OlderPagesTest`, the `LiveTest` reconnect probe
and `OlderPagesScopeTest` cover the Android rules and scope/cache interactions.

The two clients fetch older pages at different moments. Android keeps its
three-screen buffer from the start: its lazy list composes only the rows on screen,
so a page arriving above costs little. The web renders the whole history, so it
fetches what the view shows when a conversation opens (more only while the history
is too short to scroll) and keeps the same three-screen buffer once the reader
scrolls up. Its « Loading history… » banner then appears only for a reader waiting
at the start. Both keep the reader's text in place as a page arrives: Compose by
row key, the browser by scroll anchoring, with the previous manual offset at the
very top (where browsers do not anchor) and in engines without anchoring.

The paging status matches the web's `role="status"` banner on small screens: like
its 90% width, the Android pill keeps a 12 dp margin from the screen edges, wraps
the error beside a whole « Réessayer » label, and becomes a rounded rectangle when
large text wraps. It is a polite live region for accessibility services. At
normal text size the pills keep their single-line capsule look and heights.
`pagingErrorFitsANarrowScreenWithLargeText` checks a 320 dp width at 150% text.

Native ublk storage and retention: native Linux conversations use the same
on-demand S3 block journal and synchronization status as VM conversations. The
installation reclaims acknowledged clean native cache after one idle hour and
reloads missing blocks on demand. Web and Android consume the same backend status;
neither client adds a retention control. Chat and published artifact links remain.

VM nodes no longer expose a FUSE capability or diagnostic. Web removes its stale
FUSE message; Android already has no FUSE field or message. Both use the existing
execution-readiness, KVM and storage diagnostics, and the same node capability
payload is returned by public MCP and `cairn_installation`.

## Refactor campaign: current clients and protocols (2026-10-25)

Web and Android consume structured event payloads and installation-resolved plugin
setup. They no longer interpret payload-less tool/message events, JSON stored in
event text, historical wait markers, resource-based agent grants or old API save
forms. Agent previews and current grant APIs are required. Removed Android polling
workers and old web cache cleanup have no replacement migration. The relay accepts
only version 5; direct authorization accepts only version 4 and DataChannel
envelopes only version 1. The installation sends an `update_required` control frame
before closing a peer with an incompatible envelope or channel label. Both clients
stop ordinary requests and live streams on a protocol mismatch and display an
update-required message in the workspace.
Android also presents Beacon’s `updateRequired` installation status, as the web does.
Update the app, Beacon and installation together.
Network fallback from direct transport to the relay remains available. Current
activity and plugin presentation is unchanged; there is no platform difference or
new UI/MCP/installation-tool capability.
