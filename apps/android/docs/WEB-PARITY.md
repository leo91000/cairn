# Android 0.6.0 / web parity

Reference: web commit `2e9868233295af713eede804c7d70b9f514df04b` (v0.21.12).
This audit compares user actions and information, with native Android presentation.
It does not assert pixel equality between a browser and Material components.

## Platform equivalents

- Quota exhaustion appears once as an inline conversation card on both clients.
  It folds the current quota's assistant echo, failed-turn notice and failed-status
  notice, while the run activity retains its diagnostics. Recovered quota
  interruptions stay hidden in the chat after account rotation or manual resume.
  Later admission waits do not reuse a recovered turn’s error or announced reset.
  The card distinguishes
  spending from usage limits, keeps any announced reset time and zone without
  inventing a date, and offers account management to owners. An active account
  wait promises automatic recovery even while the follow-up queue is paused;
  an older failed execution offers manual resume. Android uses native Material
  controls and French copy; web uses its existing English copy and a native HTML
  disclosure for technical details.
  Coverage: `chat-quota.test.ts`, the Claude spend-limit browser journey,
  `ConversationPresentationTest`, and shared `BackgroundWaitCases` on JVM/device.

- Navigation uses Android system Back, bottom sheets and a navigation rail on wide
  windows. Chat and run readers hide the global phone navigation to maximize room.
- The agent page is a list of sections that each open as a pushed screen on every window
  size, where the wide web layout shows a left navigation next to the content. System Back
  closes a section, then asks before discarding unsaved changes (web: route guard and
  `beforeunload`).
- The web Atelier section bar stays visible on its overview and marks the overview
  icon as the current page. Android keeps its native Atelier resource cards and
  selected Atelier dock/rail item; it has no equivalent section bar.
- A subagent's activity opens in a bottom sheet on every window size, where the wide web
  layout shows a side panel. A team row opens that sheet directly instead of expanding inline.
- The plan bar opens the whole plan in a bottom sheet, where the web shows it in a popover
  above the bar.
- Android document/photo pickers and system share/save/selection replace browser
  upload/download/clipboard controls. External OAuth uses Custom Tabs.
- Attachments: the attach sheet lists recent photos from the device (asked for only when the
  user taps the tile; Android 14 limited access is supported), which browsers cannot offer; the
  web menu has Photos, Camera and Files. File actions use a long press on Android and a ⋯ menu
  on the web. Message images keep a fixed mosaic size on Android so the history does not move
  while pictures load. A single image on the web keeps its proportions; the installation records
  each new image's displayed size at upload, so the web reserves that box before it loads (older
  uploads without a size still size themselves when they load). Both viewers zoom images: pinch and pan on Android; an
  actual-size toggle with scrolling on the web. Web sharing prepares the original
  while the menu or viewer is open, then enables Share for a fresh user gesture.

  route, including files up to the 10 MiB attachment limit when using Beacon.
  They fall back to the original download route on older installations.

  and open in its full-screen viewer; browsers may show placeholders for HEIC.

  the web uses a setup modal and inline resource forms. Both keep typed secrets

  unfinished reads when leaving the screen.

  enabling changes. Closing either editor cancels the complete read on both

## Test data and privacy

Device UI captures use a local MockWebServer fixture, synthetic messages and
example.test links. They do not contain production conversations or credentials.


### Immediate wait results (#255)

Web and Android read the explicit `chat.wait_ready.payload.immediate` boolean
before the historical “Wait condition already completed” marker. An explicit
`false` keeps the result attached to the scheduled wait, even with the historical
text. Both clients also decode observations saved as JSON in `text` and replay
`tests/fixtures/activity-events.json` (the original 15 activity events plus six
wait-result cases). The event marker and reason are additive; the `wait_for`
response, stored schema and compatibility epoch stay unchanged. Older clients
can still read the event and its historical text. Cards retain their existing
native presentation and language on each platform; no layout changes.

### Older history pages (#263)

Both clients reject pages from a replaced history or stream epoch, keep accepted
pages through subsequent emissions/reconnects, and persist the combined displayed
snapshot. Android extracts these rules into the pure `OlderPages` class while the
web keeps them in `useLiveRun`.
Android also cancels a page request when its path/API Compose scope is disposed;
the web guards application with its connection generation. The lifecycle stream
resume adapters remain in place. `OlderPagesTest`, the `LiveTest` reconnect probe
and `OlderPagesScopeTest` cover the Android rules and scope/cache interactions.
See `docs/research/263-android-older-pages.md` for the discriminating experiment,
locking decision and limits; no performance gain is asserted.

The two clients fetch older pages at different moments. Android keeps its
three-screen buffer from the start: its lazy list composes only the rows on screen,
so a page arriving above costs little. The web renders the whole history, so it
fetches what the view shows when a conversation opens (more only while the history
is too short to scroll) and keeps the same three-screen buffer once the reader
scrolls up. Its « Loading history… » banner then appears only for a reader waiting
at the start. Both keep the reader's text in place as a page arrives: Compose by
row key, the browser by scroll anchoring, with the previous manual offset at the
very top (where browsers do not anchor) and in engines without anchoring.

The paging status matches the web's `role="status"` banner on small screens: like
its 90% width, the Android pill keeps a 12 dp margin from the screen edges, wraps
the error beside a whole « Réessayer » label, and becomes a rounded rectangle when
large text wraps. It is a polite live region for accessibility services. At
normal text size the pills keep their single-line capsule look and heights.
`pagingErrorFitsANarrowScreenWithLargeText` checks a 320 dp width at 150% text.

Resource-routed plugins manage participant requests on their route panel on both clients. The instance card retains approval buttons only for plugins that delegate directly through the instance. Shared plugin journeys cover both paths.

Remote dynamic plugin choices use the same query/cursor contract in all four
configuration contexts: ordinary instance, setup draft, active resource and inert
resource. Both clients retain selected IDs outside the current bounded page, show
unknown completeness separately from explicit completion, follow empty pages with
a continuation, and reject late answers after scope/edit changes. Search and page
windows stay in memory; credentials are never saved with client drafts. Web uses
the shared searchable combobox for single choices and a checkbox page for multiple
choices. Android uses native search fields, radio/checkbox choices and continuation
buttons. A missing host lookup echo is an explicit unsupported-server error on both.

Native ublk storage and retention: native Linux conversations use the same
on-demand S3 block journal and synchronization status as VM conversations. The
installation reclaims acknowledged clean native cache after one idle hour and
reloads missing blocks on demand. Web and Android consume the same backend status;
neither client adds a retention control. Chat and published artifact links remain.

Plugin detail pages on web and Android load the selected configuration, all its
instance pages, and compact saved access across packages. Public-agent choices
retain root and resource restrictions on other packages, including paused rules.
Exact current instance reads preserve concurrently changed root grants on an
older-host compatibility save; deletion is an error. Review history remains a
separate read. Both clients explicitly fall back only when the host lacks support,
and retain a supported read failure as an error. Agent/grant selectors and owner
agent-list summaries now complete the compact package, saved-instance metadata and
per-agent saved-rule count pages. They retain disabled, unavailable and removed
held access; failures keep access unknown and read-only. The selected package's
resource/profile/operation schema loads only when choosing an instance, and resource
choices omit settings and secret field names. Refreshing counts preserves an open
rule editor when the selected package/version has not changed. Names, instance
nouns and help come from the package on both clients. Shared MCP read operations
expose equivalent metadata with public scope and installation-grant checks; the
remaining generic plugin management MCP parity is still unfinished.

Shared resource OAuth controls on both clients fetch status when the owner chooses
Manage authorization / Gérer l’autorisation. An unopened provider has unknown
status. The owner's viewing choice survives a resource revision, while consent
state is recreated under that revision. Refreshing resources preserves pending
consents on unchanged resources and does not load unopened providers.

### Native continuation receipts (Slack recovery checkpoint)

Web and Android both omit the internal `chat.wakeup.delivered` receipt from chat
and run timelines. Existing wait/resumption cards and answers remain visible;
no human message row is added. This changes no management action or tool surface:
`sleep` and `wait_for` retain their existing native interfaces and authorization.
The broader Slack setup/route/OAuth mutation parity audit remains open.
